# leannginx: an nginx-compatible web server, written in Lean and proved

leannginx reads nginx configuration files and serves web pages over HTTP and HTTPS. It is written in Lean 4 and compiled to native code through C. Every decision it makes about a request (whether the request is well formed, which `server` and `location` handle it, and which file on disk answers it) is made by pure Lean code that `lake build` checks against a specification. HTTPS comes from [LeanTLS](/r/OWNER/leantls), whose TLS 1.3 server side was written for this project, and gzip from [lean-zip](https://github.com/kim-em/lean-zip), a DEFLATE implementation proved to round-trip.

## The main theorem

nginx maps a URL to a file by appending the request path to a `root` or `alias` directory. Getting that wrong is a classic source of path traversal. nginx itself is safe, but a common configuration mistake is not: `location /img { alias /data/img/; }` lets `GET /img../secret` read `/data/secret`.

In leannginx the router is a pure function that returns a small program of `stat` questions; the server answers them with real `stat` calls. The specification quantifies over every possible answer, so it holds whatever is on disk:

```latex
\forall\, \mathit{cfg}, \mathit{req}, \mathit{fs}:\quad
\mathrm{path}(\mathrm{route}(\mathit{cfg}, \mathit{req}, \mathit{fs})) =
\mathit{base}(\ell) \,/\, s_1 / \cdots / s_n,
\qquad s_i \notin \{\varepsilon, \texttt{.}, \texttt{..}\},\ \texttt{/} \notin s_i
```

where ℓ is the location the request matched and base(ℓ) is its `alias`, or else its effective `root`. This is `LeanNginx.Spec.route_confined`. The `/img..` request from above finds nothing (`vector_alias`).

## Why this matters

A test suite checks the inputs someone thought of. Attackers look for the next one: another encoding, an odd space, an unusual combination of headers. Here the claims are theorems about *every* request, *every* configuration and *every* state of the disk, and the build fails if one of them stops being true. The claims proved are the ones web servers are actually attacked through:

| Attack | Usually | In leannginx |
|---|---|---|
| Path traversal (`../`, `%2e%2e`, the `alias` off-by-slash) | a recurring bug, often caused by configuration | impossible: every file served lies under the location's `root` or `alias` |
| Request smuggling (`Content-Length` vs `Transfer-Encoding`) | serious vulnerabilities in proxies and load balancers | impossible: ambiguous framing is always rejected |
| Header injection (CR/LF in a header) | a classic in redirects | impossible: no header written to the wire contains CR or LF |
| Wrong `location` chosen | a silent misconfiguration | proved to follow nginx's rule: exact match, longest prefix, first matching regex unless the prefix is `^~` |
| Regex denial of service (catastrophic backtracking) | a known risk with backtracking engines | the matcher never backtracks, and is proved to accept exactly the regex's language |
| Corrupted compressed responses | rare, but invisible until a user reports it | lean-zip proves that decompressing the output gives back the input, for every input |

The `alias` case is worth singling out: in nginx it is a configuration mistake, not a code bug. In leannginx even a careless configuration cannot expose files outside the directory it names.

There is also no hand-written C in leannginx or LeanTLS. nginx is well over 100,000 lines of C, and memory-safety bugs (buffer overflows, use-after-free) are its main source of vulnerabilities. Lean code cannot have them: memory is managed by the runtime, and the C is generated by the compiler. (lean-zip adds four small C primitives for fast byte copies, each with a pure-Lean reference and a proof that they agree.) The decisions (is this request valid, which location handles it, which file answers it) are made by pure, specified Lean. The unspecified `Main.lean` moves bytes between sockets, TLS and files and decides nothing.

And it is used like nginx: it reads the same configuration files, so the two can be compared directly.

**Where it is not better than nginx:** it is slower (see Performance below), TLS is 1.3-only with one cipher suite, regex locations have no captures, and nobody has audited it. It is good for local development and demos. On the open internet, nginx is still the right choice for now. leannginx is not a replacement for nginx. It shows that the part of a web server that decides security questions can be proved correct, not just tested.

## What is proven

**For all inputs:**

- **Request heads (RFC 9112).** Methods and header names are tokens; header values contain no NUL, CR or LF, so they cannot inject headers anywhere they are copied. `Transfer-Encoding` is never accepted and every `Content-Length` agrees with the length used, which rules out CL/TE request smuggling. Hosts contain no `/`, quotes or angle brackets.
- **Paths.** Every segment of a normalised path is safe, whatever the client sent, percent-encoded or not. Percent-decoding inverts percent-encoding, and encoded output contains no CR, LF, space, quote or `<>`. A request path is decoded exactly once: `try_files $uri $uri/ …` can only serve the file named by the URI its location and `auth_basic` were selected on, and internal redirects (index files, the `try_files` fallback) are not decoded again, so a double-encoded path cannot reach another location's files.
- **Locations.** The selected location matches the URI; an exact `=` location always wins; a chosen prefix location is the longest matching one; a chosen regex location is the first matching one in configuration order; a plain prefix is chosen only when no regex matches. The selected `server` listens on the port the request arrived on.
- **Regex.** `regexMatches_iff`: the matcher accepts a URI if and only if the URI is in the language of the regex, as defined by the textbook inductive semantics.
- **gzip.** `gzip_roundtrip` (lean-zip's theorem): decompressing what the server sends returns the file. Compression is only used for clients that accept it and never for range requests.
- **TLS** (in LeanTLS): the server accepts only TLS 1.3, ChaCha20-Poly1305, a signature scheme the client offered and a well-formed key share it sent; ECDSA signing reproduces the RFC 6979 test vector; client and server hello messages parse with each other's parser.
- **Responses.** Header names and values written to the wire contain no CR or LF; autoindex names are HTML-escaped; byte ranges lie inside the file and `Content-Length` equals the number of bytes sent.

**Concrete vectors**, checked by the kernel: malformed and hostile request heads, URI normalisation including encoded traversal and `%00`, the full `location` example from the nginx documentation (including its `~*` regex), regex syntax and errors, `Accept-Encoding`, end-to-end routing on a test server and file system (index files, directory redirects, autoindex, `return`, 404, 405, `alias`), byte ranges, the RFC 9110 date example, ETags, server names, variables and configuration parsing.

## What it does

It reads `nginx.conf` with `include`, `server`, `listen` (with `ssl`), `server_name` (exact and wildcard), `location` (`=`, `^~`, prefix, `~` and `~*` regex), `root`, `alias`, `index`, `autoindex`, `try_files`, `return`, `error_page`, `add_header`, `proxy_pass`, `ssl_certificate`/`ssl_certificate_key` (ECDSA or RSA, chosen per name by SNI), `gzip`/`gzip_types`/`gzip_comp_level`, and the usual variables (`$uri`, `$host`, `$args`, `$scheme`, …). It speaks HTTP/1.0 and 1.1 with keep-alive and pipelining, over TCP or TLS 1.3, supports conditional requests (`ETag`, `If-Modified-Since`) and byte ranges, and writes nginx's `combined` access log. `lnginx -t` tests a configuration with nginx-style error messages.

## Performance

Measured against nginx 1.31.9 on the same 14-core laptop, with the same files and configuration (requests per second unless noted):

| Scenario | leannginx | nginx, 1 worker | nginx, 14 workers |
|---|---:|---:|---:|
| `return 200` | 23,435 | 107,474 | 106,343 |
| 628 B file | 17,494 | 38,150 | 42,171 |
| 129 KB page | **9,674** | 5,219 | 11,387 |
| 129 KB page with gzip | **12,256** | 5,291 | 31,386 |
| HTTPS `return 200` | 7,836 | 88,366 | 73,589 |
| HTTPS, one 50 MB file | 28.7 MB/s | 537 MB/s | 541 MB/s |

nginx is 2 to 5 times faster on small requests: Lean's async library runs all socket I/O through a single event loop, while nginx runs one process per core. leannginx beats a single nginx worker on larger pages and on gzip, where lean-zip also produces 8% smaller output than zlib.

Verification is what made one of the optimisations safe. LeanTLS's Poly1305 now runs a 26-bit-limb implementation that is about 50 times faster than the arbitrary-precision specification, and `Poly1305.macFast_eq` proves the two equal for every key and message. The compiler swaps in the fast version through `@[csimp]`, while every theorem keeps talking about the simple one. HTTPS bulk transfer went from 5.7 to 28.7 MB/s.

```latex
\forall\, k, m:\quad \mathrm{macFast}(k, m) = \mathrm{mac}(k, m)
```

## What you still have to trust

- **The Lean kernel**, which checks the proofs.
- **The Lean compiler, the C compiler, the runtime and libuv** (under `Std.Async`).
- **lean-zip's `bv_decide` proofs**, which trust Lean's compiled proof checker; only the gzip theorem depends on them, and the axiom audit enforces that.
- **`Main.lean` and the TLS connection loop**, which are not specified. `scripts/smoke.sh` checks them end to end with 52 checks, including hostile requests, HTTPS with ECDSA and RSA certificates, SNI, a TLS 1.2 client being refused, gzip, regex locations and 500 parallel downloads.
- **Side channels.** LeanTLS's arithmetic is not constant-time.
- **The file system.** Symbolic links are followed, as in nginx's default.

## Not built

- HelloRetryRequest, AES-GCM, session resumption, HTTP/2; regex captures, named locations, `rewrite`, `if`, `map`, `upstream` blocks.
- Request bodies with `Transfer-Encoding: chunked` get `411 Length Required`.
- `proxy_pass` speaks HTTP/1.0 to the upstream and closes the client connection after a proxied response.
